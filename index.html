03 · best work

the one that runs itself.

One project, fully defended: problem, build, receipts. This is the thing I'd want to be interviewed about.

wildfire-risk-pipeline

● live · runs hourly · 8/8 tests passing

the problem

Wildfire risk and air quality shift hour by hour, and the raw signals — temperature, humidity, wind, PM2.5 — sit in an API nobody's watching. Useful exactly when it's fresh, useless as a one-off notebook.

the build

  1. Ingest hourly. Python pulls live weather + air-quality data for 6 US cities from the Open-Meteo REST API and lands it in a Snowflake RAW schema with defined source-to-target mappings. Raw stays immutable — every output is reproducible from source.
  2. Transform in the warehouse. Three dbt models (staging → two marts) compute a 0–100 fire-risk score and classify PM2.5 into WHO/EPA health bands. API changes get absorbed in one staging model instead of breaking everything downstream.
  3. Test everything, every run. 8 automated dbt data-quality checks (not-null, accepted-values) validate every output row. Bad data doesn't reach the analytics layer, period.
  4. Orchestrate & gate. An Airflow DAG enforces ingest → dbt run → dbt test, so transforms never touch a failed load. Docker makes the whole stack reproducible; GitHub Actions runs the test suite on every push — broken SQL can't ship.

the parts a senior would ask about

Data model — grain, dimensions, facts
Star-ish layout. stg_air_weather cleans and unions the raw API pulls into one typed staging model. From it, two fact tables at a grain of one row per city per hourly reading: fct_fire_risk (region, timestamp, temperature, humidity, wind → a 0–100 score and a risk level) and fct_air_quality (region, timestamp, PM2.5 → WHO/EPA band). Region + timestamp is the natural key. Small dataset, but modeled the way I'd model a big one — so scaling it is a size problem, not a rewrite.
Data-quality strategy — why these 8 tests
The tests guard the two things that actually break this pipeline: nulls (a dropped API field silently poisons a score) and out-of-range categories (a risk level or health band that isn't in the allowed set means the scoring logic drifted). So: not_null on every column the score depends on, and accepted_values on the risk level and PM2.5 band. They run as the last DAG task — bad data fails the run instead of reaching a dashboard. What I don't test yet: unit tests on the Python extractor. That's the honest next gap (see roadmap).
Failure handling & retries — what happens at 3am
The DAG runs with retries=1 and a retry_delay of 5 minutes, so a transient API blip self-heals without me. catchup=False — if a run is missed I want the next fresh hour, not a backfill stampede of stale weather. Raw landing is append-only and immutable, so a bad transformation never corrupts source data; I can rebuild every mart from RAW. Fig. 2 shows this isn't theoretical — two runs failed and the system carried on.
Scalability — what I'd change at 100× the data
Today it's 6 cities and tiny volumes, deliberately. At 100× I'd switch the marts from full-refresh to incremental dbt models keyed on region + timestamp (only build new hours), partition/cluster the fact tables on the timestamp, and size the Snowflake warehouse up only for the transform window then auto-suspend — pay for compute by the second instead of leaving it on. The DAG structure doesn't change; that's the point of building it this way small.
Why this stack (and not the obvious alternatives)
ELT, not ETL — land raw first so every number is reproducible from source. Snowflake over self-hosted Postgres — elasticity and auto-suspend beat tuning a box for a project that runs 24×/day. dbt over hand-written SQL scripts — tests, lineage, and docs come free and the transformation is version-controlled. Airflow over cron — cron can't express "test after load, and tell me when it breaks." Docker — so it runs identically on my machine and anywhere else.
How the repo is laid out
Structured like a project meant to be read, not a notebook dump:
wildfire-risk-pipeline/ ├── dags/ │ └── wildfire_pipeline_dag.py → Airflow DAG: ingest → dbt run → dbt test ├── ingestion/ │ ├── ingest.py → pulls Open-Meteo, lands in Snowflake RAW │ └── requirements.txt ├── wildfire_dbt/ │ ├── models/staging/ → stg_air_weather.sql, _sources.yml │ ├── models/marts/ → fct_fire_risk.sql, fct_air_quality.sql, _schema.yml │ └── dbt_project.yml └── docker-compose.yaml → the whole stack, one command
Idempotency — can it re-run without making a mess?
The question every scheduler forces you to answer: what happens when the same hour runs twice (a retry, a manual re-trigger)? Because transformations live in dbt and rebuild the marts from RAW rather than mutating them in place, a re-run reproduces the same marts instead of double-counting — the transform layer is idempotent by construction. The ingestion append is the layer I'm hardening next (dedup on region + timestamp so a double-fire can't duplicate rows) — called out honestly in the roadmap.
Secrets & security
Credentials (Snowflake account, API access) live in environment variables, never in the repo — the .gitignore keeps profiles and secrets out of version control. Nothing sensitive is committed. Small thing, but a leaked warehouse key is the fastest way to fail a review, so it's deliberate.
How I'd know it broke (observability, honestly)
Today: the failed run is visible in the Airflow UI (Fig. 2), and retries=1 heals the common transient case on its own. What I don't have yet is push alerting — I have to look. Production-grade would add dbt source freshness checks plus a failure notification (Slack/email on DAG failure). I'd rather name that gap than pretend a 6-city project has an on-call rotation.
Roadmap — what ships next
In priority order: idempotent ingestion (dedup on region + timestamp); failure alerting + dbt source freshness so it tells me when it breaks instead of me checking; unit tests on the API client (pytest); a small FastAPI endpoint serving the latest scores as JSON so the marts have a real consumer; and incremental models once volume justifies it. None of these are hard — they're the difference between "runs" and "runs in production," and I know which line I'm on.

ipl-analysis

180,000+ records · 2026

Thirteen seasons of IPL cricket — two raw CSVs that didn't want to be joined. The interesting bugs in analytics are always upstream of the chart, so the work started there:

  • Profiled both datasets first — found and fixed join-key mismatches between the match file and the ball-by-ball file before a single aggregation ran.
  • Joined and aggregated 180,000+ deliveries across 800+ matches — merged the ball-by-ball file to the match file on match_id with Pandas, into per-player, per-team, and per-venue views.
  • Surfaced the patterns: top run scorers and wicket takers, team win records, whether winning the toss actually matters, and season-over-season growth.
  • Packaged it three ways — standalone script, notebook, documented README — so anyone can re-run it without me in the room.

netflix-analysis

8,800+ titles · 2025

The full Netflix catalog, 2008–2021 — 8,800+ titles of inconsistent, gap-riddled data, turned into answers about how the library actually grew:

  • Cleaned and transformed the raw catalog with Pandas — missing values, inconsistent formats, multi-value genre fields split for analysis.
  • Measured what changed: content-acquisition trends, genre distribution, and catalog growth across 14 years — with the USA measured as the top content producer.
  • Found the headline stat: TV-MA is the dominant rating at 36% of all titles — the catalog skews adult, and the data proves it.
  • Built it as a modular script, not a one-off notebook — 6 charts and a fully documented pipeline published on GitHub.

driver-drowsiness-detection

93% accuracy · academic, 2023

A real-time safety system: a CNN watching live video for driver fatigue, and sounding the alarm before it becomes a headline.

  • Built a CNN with TensorFlow/Keras trained to read the signs of fatigue from video frames.
  • Processed live video with OpenCV — frame capture, detection, and classification running continuously in real time, not on a saved clip.
  • Wired detection to action: automated alerts fire the moment drowsiness is detected — an output, not just a score on a screen.
  • Hit 93% accuracy — and learned my favorite lesson: "works in the demo" and "works continuously" are two different engineering problems. In hindsight, this project explains everything above it.
