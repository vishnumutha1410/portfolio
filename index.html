General description

This manual documents the working systems of one data engineer. Everything described here exists, runs, and can be inspected at the source.

The operator began on the analysis side and kept finding the same fault: every chart anyone trusted depended on unglamorous work upstream — reliable ingestion, sound models, tested data. He therefore moved upstream and built the whole path himself. The primary system (Section 2.1) has run on an hourly schedule since commissioning, held to production standards: version control, automated tests, continuous integration, containers, and a scheduler — not a notebook that runs once.

The operator is completing an M.S. in Data Analytics at Webster University, USA (B.Tech, Computer Science, 2023), is stationed in the Austin, TX metro, and is available for Data Engineer roles anywhere in the USA.

2.1 WILDFIRE-RISK-PIPELINE — IN SERVICE, HOURLY

TABLE 2-1 — Operating condition, system 2.1
FunctionScheduleVerificationCoverageSource
ELT: live weather & air-quality → fire-risk scores (0–100) and WHO/EPA PM2.5 bands @hourly 8/8 TESTS PASS 6 US cities github ↗

Design decisions.

  • ELT over ETL. Raw data lands immutable in Snowflake; every transformation is version-controlled SQL in the warehouse, so any output is reproducible from source.
  • Staging → mart layers in dbt. Upstream API changes are absorbed in one staging model instead of breaking every downstream table.
  • Hard DAG ordering in Airflow. Ingest → dbt run → dbt test; transformations never execute against a failed load.
  • CI as a gate. GitHub Actions runs the dbt test suite on every push; broken SQL cannot reach the warehouse.

Trade-offs accepted.

  • Hourly batch rather than streaming — matches the source's update cadence at a fraction of the complexity and cost.
  • Snowflake rather than self-hosted Postgres — paid for elasticity and zero ops instead of tuning a box.
  • Eight targeted dbt tests rather than a heavier validation framework — checks that run in seconds beat a tool nobody maintains.

2.2 IPL-ANALYSIS — COMPLETE

Exploratory analysis across 13 cricket seasons: 180,000+ ball-by-ball records from two joined CSVs. Both datasets were profiled and key mismatches resolved before aggregation — the interesting bugs in analytics are almost always upstream of the chart. Delivered three ways for reproducibility: standalone script, notebook, documented README. Python · Pandas · Matplotlib · Seaborn — github ↗

End-to-end analysis of 8,800+ catalog titles, 2008–2021: growth, genre distribution, ratings mix (TV-MA measured at 36% of all titles). Modular script with publication-ready charts. Python · Pandas · Jupyter — github ↗
